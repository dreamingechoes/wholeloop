# 0214 — Versioned CI correction production

- **Status:** Accepted
- **Date:** 2026-11-05

## Context

An original code-test failure and a proposed repair do not execute a correction. The next invocation needs a new exact-plan grant, a bounded original-feedback task, current PR ownership checks and a root containing the product actually published. Reusing every historical correction in a later route would replay an earlier CI repair against its stale published head. The frozen version-one plan does not admit a CI origin, and the public runtime document supplies no conditional merge installation.

## Decision

Introduce explicit version-two delivery plans and matching planning records. Preserve every version-one declaration and default CLI selection; opt into version two with the planning command's schema selector. The dedicated CI continuation command previews and records only the immutable next plan and private proposal receipt. It grants nothing and launches nothing. Registration recomputes the original CI/publication proof, requires a fresh exact-plan grant and refuses requirement, repository, policy or budget drift. Retain started-run limits and issued-push counts across revisions; an envelope grant remains insufficient.

Version-two corrections record their producer revision. Require known ordered unique producer revisions for CI entries, append one to every new version-two local correction, and allow the inherited version-one prefix without manufacturing producer metadata. Route only the current producer's correction while preserving its index in the full unit history. Keep the last published CI origin across intervening local QA corrections; it establishes historical ownership, never current approval.

Install a fixed read-only admission stage after plan approval and before acceptance definition or builders. Require two consecutive complete semantically stable observations, with at most three snapshots, of every original topic, open ready owned PR and bodyless current feedback. Bind repository, PR, branch, base and head. Refuse incomplete reads, moved heads, current unadopted feedback and unsupported adapters. Recheck current authority and the fixed deadline around every read; these reads supply no budget progress. Retain one consumed private intent and a closed bounded result, audit exact original bindings on inspection, and cancel only the original instance's in-memory reader. Never signal a stored PID. Builder, correction and publication entry points require that exact passed stage rather than trusting route order alone.

Start a CI producer's independent-unit workspace at the original published product head. First retain the ordinary original unit/workspace/commit-effect audit, then prove that unit's head and the declared base are ancestors of the exact published root. Local QA successors continue from their own previous unit head, which already carries that root. Existing workspace record fields hold the checked locator and head; no old record or version-one plan changes meaning. Reject a version-two proposal when any code unit has predecessors, even if the selected CI owner is independent; every code unit must be seeded and rebuilt. Unsupported dependency-bearing units remain refused.

Feed the corrector only fixed historical check failures and original observation/repair/publication digests. Keep check labels as untrusted data, preserve requirements and acceptance definitions, and require fresh verification, review, integration, acceptance and CI. Preserve the exact legacy integration/acceptance task instruction and commit message. Recompute the CI feedback projection when auditing its original production.

Publish fresh accepted candidate heads to every original owned topic and PR. Require ancestry from the exact old published head, the current grant's existing scope and push allowance, and complete fresh stable PR/head/feedback reads before each step. Use ordinary non-force Git pushes only. The create and ready effects positively observe the same existing ready PR; they never create a replacement or edit its body. Its original acceptance text remains historical. Updating that text would require separately granted PR-update work; current evidence stays in the new core receipts. Reconciliation binds the original PR URL rather than accepting another matching marker.

Expose shared implementation composition to trusted installed SDK code only. A to-merge SDK route still requires fixed CI/merge hosts, matching identities and the existing independent installed runtime allowance; plan and grant alone cannot install it. The public composer supplies no installation, still rejects to-merge, and adds no native-runtime flag or credential authority. Keep wider envelope and credential proposals separate.

Separate the pure publication marker/ledger reader from the execution controller. This avoids importing acceptance execution through lifecycle registration and workspace seed checks. A regression exposed the actual module cycle before this separation; retain that failure and its passing controls.

## Alternatives rejected

Changing a frozen version-one enum would make old declarations lie. Replaying all correction history would ask the second repair to admit the first repair's obsolete head. Starting from a unit topic could discard integration changes present in the failed published product. An empty comment fallback or historical read would hide current feedback. Force pushes, replacement PRs, implicit PR-body edits and automatic comment adoption would widen authority. A public runtime merge flag would cross a separate installation boundary merely to make a fixture run.

## Verification

Component controls exercise explicit CLI selection and cold-process proposal reads, unchanged frozen declarations, fresh exact grants, no-write previews, original budget ceilings, producer revision routing, complete stable feedback and cancellation, missing/rehashed receipts, actual Git ancestry and original-PR publisher effects against a stub host. They certify no native client/model, containment or hosted account. The SDK's actual Git/Docker execution records all required current stages and the original PR's second non-force push, then blocks ungranted merge. Preserve its first producer-reason failure and second reporter-cache failure as failed commands. The fixed verifier, shared by the evaluation entry point, passes fresh API/bare-object readback of the latter's retained core execution without another worker, grant or journal event; report SHA-256 `ff40ecf01f32b20b89a68cb365bacef3b7baab619aff7c462cf7f81c2eaa7b87`. The live command was not repeated after the reporter-only correction. Exactly two pushes, no merge effect and all four retired environments are checked. Additional differential controls reproduce missing original-topic scope, a later spent push allowance, another dependent code unit and replacement-PR readback before their conservative guards. Linux arm64 Node 20.0.0 and 24.22.0 SDK component checks pass offline; an initially colliding standalone banner is corrected using the project's existing aliased ESM shim. The integrated final tree passes 499 focused tests in ten files; strict types, harness, links and Markdown prechecks also pass. Mandatory fast and complete gates remain required before task closure.
