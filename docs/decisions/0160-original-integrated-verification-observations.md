# 0160 — Original integrated verification observations

- **Status:** Accepted
- **Date:** 2026-10-29

## Context

A root integration stage needs recoverable whole-product evidence. A retained JSON report proves its bytes, but a passing report or the latest individual case cannot establish which candidate, assembly and original attempt produced its claims. Recovery must also survive later corrections and exact environment retirement without querying Docker or replaying cases.

Environment runtime revisions change as cases register resources. Requiring identical runtime revisions across every case and the final report incorrectly rejects actual combined observations. Ignoring runtime revisions entirely would accept unsupported environment claims.

## Decision

Reopen the exact budgeted report artifact and original immutable candidate, assembly and pre-builder acceptance definition. Recompute complete criterion, contract and procedure coverage. Require machine-owned cases and the exact candidate/assembly/environment case keys used by the fixed integration executor, with each case's original Docker effect, assertions and captures from ADR-0159. Recompute the ordered case vector, checks, repair ownership, status and delegated-machine claim. Preserve a known first failure and reject borrowed results after that failed prefix. Refuse human, incomplete, stale or unsupported reports instead of manufacturing a historical pass.

Resolve every runtime binding through the original environment snapshot chain. Validate the entire chain, including later snapshots, before returning a requested historical revision. Require the report's historical environment to be ready and bound to the exact original run, plan, grant, recipe and combined candidate vector. Individual cases must share those immutable inputs and cannot name a revision after the report's original revision. Private evaluation still requires its existing original sensitivity proof.

This reader has no Docker driver or execution selector, grants no authority and changes no journal. It returns historical assertion proof with native ownership and current acceptance explicitly not-established. Root integration completion must separately join current unit/assembly readiness, original native ownership and the original controller deadline. The public whole-route runner remains unfinished.

## Alternatives rejected

Trusting content-addressed report bytes alone accepts fabricated coverage and status. Selecting latest case results mixes attempts. Comparing mutable runtime revisions as if they were immutable candidate identity rejects real CLI executions. Ignoring those revisions loses original environment proof. Replaying cases during status recovery repeats effects and budget consumption. Treating this historical result as current acceptance skips independent readiness and native-scope checks.

## Verification

Run directed unsupported-input controls and full-chain historical-runtime checks. Extend the existing actual two-repository Docker evaluation while retaining its original green-isolated/failing-combined scenario, correction, unchanged case expectations and deadlines. Reopen failed and successful reports, refuse changed status, coverage, case evidence, runtime bindings and repair claims, and recover identical evidence while paused after exact retirement without journal writes. Record execution results and any initial failures in the journal before committing. Keep authenticated models, independent Linux application-host acceptance and complete-route execution separate.

All eleven actual combined controls pass on macOS Node 24.22.0, including eight substituted-report refusals and paused recovery after both exact environments retire. Complete isolated Linux checks pass 3346 tests in 176 files and all remaining checks. Historical recovery preserves identical evidence/journals on Linux Node 20.0.0 and 24.22.0. The journal retains the initial mutable-revision and enforcement-rule failures rather than relabeling those snapshots.
