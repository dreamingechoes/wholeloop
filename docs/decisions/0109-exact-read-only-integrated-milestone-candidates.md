# 0109 — Exact read-only integrated milestone candidates

- **Status:** Accepted
- **Date:** 2026-10-25

## Context

Independently passing parts do not identify an integrated application. Missing predecessors, a moving target or an unrecorded recipe change can make a previous result irrelevant. Preparing a description must not acquire merge, execution or publication authority.

## Decision

1. Derive the complete milestone and work predecessor closure from the accepted delivery plan. Pin every required committed part, repository/base/topic/assembly SHA, contract revision, acceptance definition, environment recipe, data input, verify/review requirement, guidance identity and repair owner. Validate closed dependency graphs and criterion coverage before observing Git.
2. Observe canonical registered clean topic/assembly worktrees, common Git ownership, declared push destinations, current named target bases, predecessor ancestry and required-part inclusion. Refuse the personal checkout, target branches, missing or dirty parts and mismatched contract versions. Observe snapshots twice to detect concurrent changes. Preparation performs no Git mutation or network request.
3. Retain immutable digest-bound candidates in the external store. Inspection reobserves current inputs; historical reads remain available. A moved target produces an explicit blocked result rather than silently accepting a new base. Compare complete input identities conservatively; equality never authorizes execution reuse.
4. Treat supplied assembly commits as observed proposals. P6-19 owns actual controller-created assembly, conflicts and whole-product execution. Gate-policy inputs bind requirement bytes, not passing receipts. Every prepared record explicitly leaves execution/publication unperformed and acceptance unestablished. Multiple repositories identify one vector without claiming an atomic deployment or automatic rollback.
5. Keep preparation usable before a live runner exists. For registered runs, require the latest accepted delivery basis. This creates no authority; later execution must establish its own original grants, effects and current candidate checks.

## Alternatives rejected

Hashing only worker heads omits target, acceptance and execution inputs. Trusting caller-selected parts silently drops predecessors. Automatically refreshing bases changes the approved scope. Treating a manually assembled branch as controller provenance or passing QA turns metadata into authority. Requiring a remote service to prepare a local candidate adds accounts without strengthening these local observations.

## Verification

Use disposable actual Git repositories, generated DAGs and protected-file invalidation tables. Exercise two-repository vectors, dirty/missing/uncommitted predecessors, changing destinations/bases, contract revisions, repair ownership and preserved personal/worker files. The model-free integration evaluation retains its report outside the repository; it does not certify combined application behavior, native clients, accounts or publication.
