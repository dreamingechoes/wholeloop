# 0249 — Delivery supervisor service

- **Status:** Proposed
- **Date:** 2026-11-08

## Context

A delivery run executes in an owned foreground controller that a person starts with `wl delivery run`; the queue keeps durable work slots with journaled reservations ([0097](./0097-durable-queue-reservations-and-current-attempt-fences.md)), and recovery and reconciliation never replay an issued effect. Nothing takes queued work by itself, resumes a run after the machine restarts or continues a run paused by an exhausted usage window ([0209](./0209-controller-owned-native-credentials.md)). A factory that works around the clock needs that loop without giving it any authority a person did not grant.

## Decision (proposed)

- Add `wl delivery supervise`, a long-running process that loops over three duties: start the next admissible queued work under its existing grant and budget, reconcile any run whose controller is gone and resume it when its recorded state allows, and resume runs paused for a usage window once the window has reset.
- It is a coordinator only. It starts the same owned foreground controller a person would, holds no credential of its own beyond what [0209](./0209-controller-owned-native-credentials.md) gives each run, and never issues a grant, extends a budget, merges or retries an effect whose outcome is unknown.
- One supervisor per store, enforced with the store's writer-lock rules; a second instance refuses to start. It keeps no state outside the journal, so stopping and restarting it loses nothing.
- Run it under the operating system's service manager: a launchd agent on macOS and a systemd user unit on Linux, generated by `wl delivery supervise --install` for the operator to review and load. The process stays in the foreground under that manager rather than daemonizing itself.
- Its activity appears in the existing overview and change feed ([0210](./0210-operator-overview-and-change-feed.md)).

## Alternatives rejected

- **A cron entry per command.** Overlapping invocations race for the same work, and cron cannot tell a crashed controller from a running one.
- **A hosted scheduler.** It would move execution off the operator's machine and its containment.

## Consequences

Runs no longer need a person to start or restart them. Everything the supervisor does is something an operator could already do by hand, under the same journal and authority checks.

## Verification

Process tests for the single-instance lock, a kill-and-restart rehearsal mid-run, a window-reset resume with a synthetic usage signal, and one live overnight scenario.
