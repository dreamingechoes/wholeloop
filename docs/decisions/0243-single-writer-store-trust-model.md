# 0243 — Single-writer store trust model

- **Status:** Accepted
- **Date:** 2026-11-06

## Context

The runner re-observed every fact at every internal guard as if another program could rewrite the store or the repository between two lines of the same decision. Each store access canonicalized its path twice and probed for repository markers on every ancestor up to the filesystem root, and the delivery base guard started five Git processes for every guard of a decision. In the measured EVAL-09 route this was most of 3.2 million `existsSync` calls and 3546 of 6302 Git processes. Collecting a missing path's suffix also shifted every earlier component.

The store's writers are known: only `wl` processes write it — the waiting CLI, its controller, owned wrappers and concurrent `wl` commands. Planned user interfaces only read it and submit input through `wl` commands. What genuinely changes from outside is the person's repository, the Docker daemon and process state.

## Decision

Trust the store's own writers and keep observing what is external.

- **Single writer.** Only `wl` writes the store. Dashboards and notification tools read projections and the read-only change feed and submit decisions through `wl` commands. Locks, atomic replacement, journal hash chains and committed-fact flushes remain, because several `wl` processes run concurrently and can crash.
- **Store containment per root.** Resolving a root still canonicalizes it twice and refuses repository markers on every ancestor. An access below a root this process resolved canonicalizes once, refuses an escape from the root and probes markers on the root itself and on the components below it, which `wl` creates. A marker added above an already resolved root is refused by the next resolution. Any other boundary keeps the complete walk. Missing suffix components are collected leaf-first and reversed once. Containment of two absolute paths with no empty, `.` or `..` component and no trailing separator is a component-prefix comparison; any other pair still goes through `path.relative`. The guarded byte reader, given a resolved store root, canonicalizes the target once and keeps containment, `O_NOFOLLOW|O_NONBLOCK`, the regular-file, size and EOF proofs and the before/after descriptor comparison; the second canonicalization and final identity `lstat`, which defend against another program replacing a file mid-read, run only for other roots such as repositories and sources.
- **External facts once per decision.** The base guard reuses its last successful observation only within the same synchronous job and only while this process has announced no effect: every store mutation, launch and Git write increments an effect counter, and the observation expires when the job ends. A refusal is never reused; sealed read observations keep their own reads. The private review patch between two content-addressed trees of the store's object directory follows the same rule; callers still compare its digest with the journal every time. One helper, `DecisionMemo`, holds both: it stores nothing when the read refuses or itself announces an effect, and keeps at most a few keys. The repository's local configuration is deliberately not memoized: two independent actions can run back to back in one job, and a helper configured between them must refuse the second.
- **Fewer processes per observation.** `repository()` asks for the top level and the common directory in one `rev-parse`; the base guard adds the verified commit of `target^{commit}` to that same query and keeps the symbolic resolution and remote URL as separate queries. A joined answer is used only when it is exactly the expected number of newline-free lines; any other output runs the original separate queries. Every failure of the guard is the same refusal, so only the accepted set must match, and it does: acceptance requires the symbolic name to equal the requested ref. A workspace snapshot asks for `HEAD` and `--symbolic-full-name HEAD` in one `rev-parse` instead of `rev-parse HEAD` and `branch --show-current`; commit ownership adds `--absolute-git-dir` and the symbolic `HEAD` to the identity query. The symbolic answer must be `HEAD` (detached, an empty branch) or a `refs/heads/` name; a failure, any other answer or an unexpected shape reruns the original queries in their original order, so outputs, error messages and their priority — including the refusal of a `HEAD` outside `refs/heads/` and an unborn branch — are unchanged. Inside a sealed read observation both keep the original queries: there each query is shared by key with every other reader of the observation, and a joined query would add a process instead of saving one — measured as six to eight more Git processes in each of the acceptance, publication and handoff phases before this exception.

This supersedes the earlier requirement that every store access repeat the complete ancestry walk so that a marker inserted and removed between two sibling accesses is refused; that protected against an adversary writing in or above the store during one decision, which is outside this model.

## Alternatives rejected

Caching a root's verification for the whole process would let a new resolution miss a later repository. Caching base observations across awaits or effects would let a decision act on a base observed before its own push or merge. Reading refs from the filesystem bypasses packed refs and Git's resolution rules; listing staged and untracked paths in one `ls-files --stage --others` call cannot separate an untracked name that mimics a stage entry, so the snapshot keeps both calls; reimplementing `remote get-url --push --all` would have to reproduce `pushurl` and `insteadOf` exactly.

## Verification

`test/unit/state/store-root-containment.test.ts`: an access 4 or 16 levels below a resolved root makes at most eight `existsSync` calls (34 and 58 before); markers inside the store or at its root still refuse, as `test/unit/delivery/journal.test.ts` requires; a marker above the root is refused by a new resolution; an escaping link still refuses; a store read makes one `realpathSync` call where any other root makes three, and symbolic-link and FIFO targets in the store still refuse. `test/unit/worktrees/git-joined-queries.test.ts` compares every joined answer with the original queries across primary and linked checkouts, spaces and newlines in paths, bare repositories, missing, nested-ambiguous, remote-tracking, tag and tag-pointing targets; shows one process for `repository()` and three for a remote-bound guard; and shows reuse within one job and renewal after an await, a Git write and a store mutation; it also compares the joined `HEAD`/branch and ownership queries, including their errors, with the original ones for named, nested Unicode, detached, symbolic-chain and tag-pointing branches, a `HEAD` outside `refs/heads/`, unborn branches, newline paths and bare repositories. `test/unit/review/review.test.ts` shows the same reuse for the private review patch, and `test/unit/state/decision-memo.test.ts` the helper's expiry, size bound and unrecorded refusals; `test/unit/evaluation/live-implementation.test.ts` still refuses a hook path configured between two back-to-back configuration checks. `test/unit/gates/snapshot-observation.test.ts` counts three Git processes per snapshot capture. `test/unit/state/path-suffix-performance.test.ts` removes the quadratic suffix shifts; `test/unit/state/path-containment.test.ts` compares containment with the former `path.relative` answer for more than 50 000 generated pairs, including `.`, `..`, empty, dotted and trailing components, and shows normalized pairs never call it. The repository-marker controls in `test/unit/state/read-observation.test.ts` keep their complete walk because their boundary is not a resolved root.
