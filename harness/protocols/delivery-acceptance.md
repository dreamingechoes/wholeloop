# Delivery acceptance evidence

- ⛔ `delivery-acceptance-coverage` — pin complete criterion coverage, inherited human/machine ownership and explicit applicability before execution. Failed evidence cannot waive or rewrite its definition. Wrong source/plan/candidate or incomplete assertions never establish acceptance.
- ⛔ `delivery-acceptance-observation` — accept execution facts only from trusted controller hosts bound to the current private grant, exact invocation and owned application. Import no worker JSON as process/human proof. Preserve unknown invokers, current-input invalidation and ordered failures. Fixtures remain fixture-only; historical human testing never becomes delegated acceptance or a current human observation.
- ⛔ `delivery-acceptance-artifacts` — retain bounded content-addressed evidence externally under finite run accounting. Scan complete bytes for recognizable credentials before chunking, verify observed chunks on reads and refuse symlink/metadata escapes. Capture and sealing authorize no sharing or TTL deletion; missing or omitted required evidence cannot become a pass.

A prepared acceptance plan executes nothing. Objective behavior hosts and independent evaluators supply observations; an agent's result is a claim until the controller binds actual execution and evidence. Human-only criteria remain pending until an explicit named operator note on the exact candidate. Existing suite/gate policies and original supervised records remain unchanged.

⛔ `delivery-private-acceptance` — Keep pinned evaluator inputs outside builder workspaces and actual evaluator mounts separate. Applicable regression acceptance requires the unchanged case to fail on the clean base and pass on the current candidate; fixture claims, native counters and model statements never prove private boundaries or semantic sensitivity.

⛔ `delivery-browser-execution` — Execute browser cases only through the pinned private-stdio host and observed owned page context. Ground controls in selected inputs and fresh native references; require objective assertions and backend roundtrips for persistence. Screenshots and worker claims establish neither persistence nor human approval.

⛔ `delivery-behavior-execution` — Execute objective API/CLI cases only through the fixed declared behavior host on the exact owned application; preserve incomplete responses, unknown effects, actual process/exit facts and original suite/gate budgets. A green unit suite cannot substitute for acceptance.

⛔ `delivery-integration-candidates` — Bind every required committed part, repository/base/assembly revision, contract and complete protected input before preparing an integrated milestone. Refuse dirty or missing predecessors and moving bases. Read-only preparation and input equality establish no assembly provenance, acceptance, execution reuse or publication authority.

⛔ `delivery-integration-assembly` — Create and merge only exact controller-owned topic worktrees under original scoped grants, per-step effects and finite repair budgets. Preserve conflicts and partial outcomes; never reset workers or targets, replay unknown Git writes or infer whole-product acceptance from isolated green parts. Require current complete assembly/environment vectors and pinned contract/procedure cases; milestone evidence grants no publication or rollback authority.
