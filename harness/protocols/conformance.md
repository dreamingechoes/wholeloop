# Conformance evidence

- ⛔ `remote-dashboard-create-boundary` — bind explicit create authority to the
  exact completed artifact/query and reviewed deployment/datasource/folder.
  Journal intent before writes, verify stored identity/content, keep credentials
  in the host store and retain ambiguous outcomes without retries or overwrites.

- ⛔ `remote-flag-read-boundary` — keep service execution explicit and credentials
  in the host store. Bind exact read identity, bound/redact transport, refuse
  mutation routes and normalize only supported complete targeting. Unsupported
  or failed reads stay unknown, never an inferred disabled flag or percentage.

- ⛔ `conformance-nightly-authority` — keep native execution and issue delivery
  separately activated. Reuse exact transferred core/result bytes, isolate each
  selected key/channel home, upload only structural evidence and serialize issue
  writers. Missing configuration stays UNRUN; mutate no source page or ref.

- ⛔ `conformance-exact-acquisition` — bind the whole batch to exact official
  package/platform/version paths before installing. Keep installation explicit,
  external and credential-free with separate prefixes; verify available integrity,
  archive safety and installed identity. Preserve missing checksum evidence and
  partial outcomes without pretending top-level pins freeze vendor dependencies.

- ⛔ `conformance-issue-projection` — draft only fresh comparable structural
  regressions with stable markers and consumed metadata. Keep delivery explicit,
  refuse partial issue inventories or changed/old-core artifacts, check open/closed
  markers and current freshness, and preserve partial outcomes without retries.

- ⛔ `conformance-explicit-collection` — validate the complete exact-version batch
  before preparation, require explicit fixture/live mode and every selected native
  channel binary, and create fresh external runs. Keep crash reports and continue;
  stop new preparation on cancellation. Omit journal paths from matrix artifacts.

- ⛔ `conformance-evidence-boundary` — preparation starts no model. Installed-core
  simulations remain FIXTURE_PASS with simulation evidence; they never close the
  actual native-client matrix. A live structural PASS requires an explicitly live
  process, exact observed version, successful exit and the required journal chain.
- ⛔ `conformance-fresh-fixture` — prepare a new external fixture for each run.
  Bind source/scenario/core hashes, retain the owned standalone initiative and
  installed-skill marker, and preserve the observed repository baseline. Do not
  resume, retry or relabel a claimed fixture. Inspect failures before starting over.
- ⛔ `generated-distribution-not-guidance` — discovery excludes native-looking
  copies under .wholeloop/distribution, including internal aliases into that tree.
  Installed overlays and actual repository guidance remain eligible.
- ⛔ `conformance-matrix-observations` — keep unrun, simulation and native reports
  distinct. Retain actual observation time and requested/observed versions; reject
  reused runs and inconsistent successful reports. Stale evidence proves no
  current native support. Imported reports are not authenticated attestations.
- ⛔ `conformance-regression-comparability` — a version regression candidate needs
  fresh native pinned PASS/latest FAIL on different exact observed versions,
  successful processes, identical core/source/scenario bindings and named failures.
  Launch/authentication failures and incomparable runs need separate diagnosis.
- ⛔ `conformance-explicit-page-projection` — compare supplied matrix documentation
  with an explicit destination/time and write only on request. Require one owned
  section in a regular bounded page without linked parents. Preserve surrounding
  prose, original observation dates and evidence limits; persist no raw reports.

This scenario checks process/journal structure. It does not establish native
protocol correctness, semantic evidence quality, hook activation, permission
isolation, executable provenance or complete absence of external side effects.
Keep authentication in the client's existing store and preserve native permission
and trust checks. Never promote unobserved behavior to a conformance checkmark.

Use `conformance diagnose <run>` after a new live attempt. Categories omit native
text and do not prove root cause. Keep the scenario verdict separate: a zero exit
with missing journal events still fails. Missing legacy diagnostics stay unknown.
Resolve access/trust through the native client; do not add blanket grants or
replace accounts/models automatically to turn a failure into a pass.

- ⛔ `conformance-redacted-diagnostics` — persist only closed error/event categories
  and counts. Do not retain raw native prose, private tool payloads or credentials.
  Classification never changes the journal-based scenario verdict.

- ⛔ `conformance-scripted-final-approval` — bind the fictional fixture owner's
  declaration to exact final bytes and decision. Require same-run final review;
  changed bytes need a new declaration. Keep simulated review visibly simulated.
  This test declaration never substitutes for a real person's approval.
